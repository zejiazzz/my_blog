# 多智能体规则

## Agent 类型与用途

| 类型          | 用途                 | 何时使用                                     |
| ------------- | -------------------- | -------------------------------------------- |
| **Explore**   | 代码探索、搜索、调研 | 不确定实现范围、需要多处搜索、跨模块链路分析 |
| **Plan**      | 架构设计、任务拆解   | 中高风险需求的设计阶段                       |
| **Implement** | 代码编写、文件修改   | 实际编码执行                                 |
| **Review**    | 验收检查             | 完成后的独立验证（只读，不写文件）           |

## 使用原则

- 简单任务主 agent 直接完成，不创建子 agent
- 中高风险任务在 `docs/plans/active/<feature-slug>-spec.md` 的 A 节中明确 agent 分工
- 多 agent 按复杂度启用，不作为所有需求的默认流程
- 子 agent 职责单一，避免多个 agent 修改同一块代码
- 并行 agent 写入范围必须互不重叠
- 写入同一文件的任务必须串行，写入不同 module 的任务可并行

## 触发时机

- 根据任务复杂度决定是否需要多 agent，不为形式强行启用
- 复杂需求按任务类型拆分：需求梳理(Explore)、架构设计(Plan)、代码实现(Implement)、验收(Review)
- 用户明确说"单模式"时，不主动创建额外 agent
- 用户明确说"多模式"或"带验收"时，启用多 agent；简单任务仍可由主 agent 完成

## 验收 Agent

- 所有代码改动必须由主 agent 完成自检，覆盖需求点、已满足项、未满足项、存疑项、风险与回归点、验证结果
- 中高风险需求或用户明确要求"带验收"时，补一个只读 Review agent
- Review agent 对照 `docs/plans/active/<feature-slug>-spec.md` 的 R 节逐条验收
- 验收不通过时，先修实现，再重新验收
- 只有稳定复发规则缺失时才回写 `.rules/`

## 可用角色

- **产品 agent**：需求分析、功能设计、用户体验规划
- **前端 agent**：UI 实现、交互逻辑、组件开发
- **后端 agent**：API 设计、数据处理、服务端逻辑
- **UI agent**：视觉设计、样式实现、响应式布局
- **测试 agent**：测试用例、质量验证、回归测试
- **运维 agent**：部署配置、性能优化、监控告警

## 分配原则

1. **简单对话/咨询**：无需启动 agent，主 agent 直接回答
2. **单一技术问题**：启动 1 个对应角色的 agent
3. **功能开发**：根据需求复杂度启动 2-3 个 agent（如：产品 + 前端，或产品 + 前端 + 测试）
4. **完整需求**：启动 3-5 个 agent，产品 agent 必须参与需求完善

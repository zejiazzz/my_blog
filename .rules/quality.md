# 质量与注释规范

## 沟通规则

- 默认用中文解释，结论先行，只补充必要信息
- 对用户回复里提到的仓库文件，默认使用绝对路径；项目内文档示例可以使用仓库相对路径
- 如果跳过某个检查，要明确说明原因，不要假装已通过
- 不确定时直接说明不确定；需要用户决策时只问关键问题

## 实现原则

- 写代码或设计方案前，先确认目标、边界、验收、约束和风险；不清楚且影响实现方向时，先问关键问题
- 先理解现有实现，再决定怎么改
- 从用户真实目标、当前约束、最小可验证结果出发，不直接套用惯性方案
- 做小而完整的改动，只解决当前问题，不顺手重构无关功能
- 目标清晰但路径不优时，先指出更短或更稳的做法；低风险时可说明假设后继续推进
- 同一思路连续失败时要换思路，不要反复死磕
- 涉及多个文件变更时，先确认范围和影响再继续
- 不新增未被要求的框架、依赖、全局状态或复杂抽象
- 遇到用户或其他 agent 的已有改动时，必须保护并绕开，不格式化或重写无关文件

## 编码前检查

开始写代码、设计方案、修复缺陷或重构前，至少确认：

- 目标：这次真正要解决什么问题，用户希望看到什么结果
- 边界：哪些文件、模块、入口、页面或行为在范围内，哪些明确不碰
- 验收：怎样证明完成，包括可见行为、测试、构建、日志或人工验证路径
- 约束：是否涉及 AGENTS.md、已触发 skill、模块架构、兼容性、性能、发布时间或三方文档
- 风险：是否可能误解需求、扩大影响面、破坏主流程或覆盖已有改动

如果任一项无法可靠推断，且不同答案会导致不同实现，应先澄清；只有风险低且可合理假设时，才说明假设并继续。

## 先提问与直接执行

以下情况先问关键问题：

- 用户只描述方案，未说明要解决的业务问题，且该方案可能不是最优
- 需求存在多个合理解释，不同解释会导致不同数据模型、接口、页面、路由或状态流改动
- 验收标准不明确，无法判断完成与否
- 改动可能影响主流程、付费/权益、登录态、发布配置、数据删除、线上兼容或跨端行为
- 需要在"快速补丁"和"架构调整"之间取舍，但用户没有给优先级

以下情况可以直接执行：

- 目标、边界、验收标准已经明确
- 改动范围小、风险可控，且能通过阅读代码推断正确做法
- 需要先做代码调查、复现、定位或只读分析来澄清事实
- 用户要求的路径不是最优但无明显风险；此时可提示更优路径，并按用户选择或低风险假设推进

## 注释规范

- 代码注释和文档注释默认使用中文；如果局部文件已有统一英文约定，则遵循原约定
- 公共入口、导出 API、不够直观的变量需要补简洁说明
- 新增或修改状态字段、资源路径、尺寸常量、私有方法、布局约束、兼容分支时，默认补一句说明意图
- 复杂参数、返回值、异常语义、平台差异、历史兼容、异步时序、状态流转和性能取舍需要说明约束或原因
- 注释解释"为什么这样做"或"规则是什么"，不要逐行翻译代码
- TODO 必须写明后续处理方向、触发条件或待确认问题，不留下只有占位含义的信息

## 验证与验收

### 验证分层

- 简单 UI、文案、资源、注释调整：只读代码检查即可
- 共享逻辑、公开契约、生成代码、长链路：运行最相关检查或测试
- 临时新增的验证代码在验证通过后必须删除
- 对生成代码或生成文件，要用独立只读过程验证结果
- 生成的文件都需要执行格式化
- 执行型 spec 统一放在 `docs/plans/active/`，长期知识文档统一放在 `docs/specs/`

### 自检清单（所有代码改动）

- 凡涉及代码改动，最终回复前必须覆盖：需求点、已满足项、未满足项、存疑项、风险与回归点、验证结果、结论
- 自检时确认目标、边界、验收标准已明确；不明确处已经提问或声明低风险假设
- 自检时确认改动范围最小且完整，没有覆盖用户或其他 agent 的已有改动
- 自检时确认必要中文注释已经补齐，复杂逻辑和非直觉取舍已说明原因
- 中高风险需求或用户明确要求"带验收"时，补只读 Review agent；其他代码改动由主 agent 自检即可

### 纯分析/文档任务

- 纯问答、纯分析、纯文档润色、只读调研类任务可跳过验收 agent；如未改代码或未运行检查，需要说明原因
